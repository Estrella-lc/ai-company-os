# AI 产品技术栈与能力边界 · 学习笔记

> 面向非工程背景的产品人。目标不是学会写代码，而是能看懂一个 AI 产品是怎么搭起来的、AI 在哪几层能做事、哪几层不能。
> 整理时间：2026-11-22

---

## 一、先建立整体地图：七层技术栈

任何一个现代 AI Web 产品——包括你那个 `ai-company-os-web`——都可以拆成七层。**越往上越确定、越可靠；越往下越智能、越不确定。**（这里的"上"指下面列表的 1→7 顺序）

| 层 | 技术 | 职责 | AI 该参与吗 |
|---|---|---|---|
| 1 前端 | Next.js、React、TypeScript、Tailwind | 页面与交互 | 只生成代码，不参与运行 |
| 2 接口 | API Route Handlers | 身份校验、参数校验、权限 | 否，规则必须写死 |
| 3 数据 | Postgres、RLS、pgvector、Storage | 存业务状态、文件、向量记忆 | 只读写，不决策 |
| 4 边缘 | Edge Functions（Deno） | 靠近数据库的无服务器逻辑 | 可承载 AI 编排 |
| 5 编排 | Worker、任务表、租约、重试 | 认领任务、断点恢复 | 否，纯工程 |
| 6 执行 | Sandbox、外部工具、ComfyUI | 真正产出文件 | AI 只能发号施令 |
| 7 智能 | Claude / OpenAI、Agent 框架 | 理解意图、规划、生成 | 是，但能力有边界 |

**核心判断**：前六层是确定性的工程（做对就是做对），第七层是概率性的智能（可能出错）。你之前项目"感觉不聪明又看不懂"，本质是把第七层的期望，压在了前六层的结构上——一个工单流转系统，再怎么加 AI 也不会像"公司"。

## 二、每层学到什么程度（够用标准）

### 1. 前端 — 懂概念即可
- 知道"在网页提交一个目标"本质是一次 HTTP 请求，页面只是入口。
- 知道 `page.tsx` 是页面、`components` 是界面零件。不需要会写。

### 2. 接口 — 懂原则
- 知道 API Route 是前后端之间的门卫：校验身份、检查参数、判断权限。
- **产品原则**：这层不能交给 AI 自由判断，必须是写死的规则。所有"AI 会不会乱来"的担忧，都在这层用工程手段兜住。

### 3. 数据 — 重点学
- **Postgres**：关系型数据库，存结构化业务状态（任务、进度、用户）。
- **RLS（行级安全）**：数据库层面保证"用户 A 看不到用户 B 的数据"，不用自己写过滤逻辑。
- **pgvector**：把文本/图片转成向量存起来，实现"语义搜索"和 AI 长期记忆。100 万行以内够用。
- **Storage**：存生成的文件（图片、视频、报告）。
- **产品意义**：AI 的"记忆"问题，工程上就是往这层读写。想要 AI 记住什么，就得设计一张表。

### 4. 边缘函数 — 懂定位
- 跑在离数据库很近的无服务器环境（Deno），自动扩缩容、支持流式输出。
- 你项目的 `cto-task-worker` 就在这层：认领任务、续租、分派执行。

### 5. 编排 — 懂机制
- 任务表 + worker 认领 + 租约（lease）+ 超时续租 + 失败重试。
- **产品意义**：这层决定"AI 中途崩了能不能恢复"，跟智能无关，纯工程可靠性。你 README 里"租约过期可恢复"就是这层的功劳。

### 6. 执行 — 懂边界
- Sandbox 隔离执行、外部工具调用、ComfyUI 这类生成引擎。
- **关键认知**：AI 只能发号施令，工具成不成功它控制不了。所以"找好用 skill / 成熟技术"这件事，本质是给这层接更多可靠的工具，不是让 AI 更聪明。

### 7. 智能 — 重点学
- 模型只做三件事：理解输入、规划步骤、生成文本或工具调用。
- 框架选择（2026 现状）：
  - **CrewAI**：角色分工直观，适合快速原型、非技术人能看懂
  - **OpenAI Agents SDK**：交接（handoff）概念简单，和 Codex 同生态
  - **LangGraph**：状态图，生产级、可控，但学习曲线陡
  - **AutoGen**：对话式多智能体，适合研究，不适合面向用户的产品
- **共识**：先做单 Agent + 强工具的验证，再考虑加编排复杂度。很多"框架失败"其实是模型能力不足伪装成的。

## 三、AI 的真实能力边界（2026）

### 能稳定做（真实可用）
- 5–20 步、边界清晰的任务
- 范围明确的工程工单：成功率约 65–80%
- 代码重构、迁移、写测试
- 有明确问题的网页研究、文档抽取
- 邮件分类、日程协调这类琐事

### 做不到（别押注）
- 跨天跨周的长期自主任务
- 需要真正判断的事：设计、战略、审美、招聘
- 50 步以上不丢失目标
- 多智能体自发协调（开销常大于收益）
- 要求 95%+ 准确率的场景（实际只能到 80–90%）
- 没有人工审批的高风险操作
- 持续的创造性打磨（能起草，不能独立迭代到精品）

### 三个必须记住的数字
- **95% → 60%**：单步 95% 成功率，连续 10 步后只剩 60%（0.95¹⁰ ≈ 0.60）。这就是"流程越长越不可靠"的数学原因。
- **30–40 步**：超过这个长度，Agent 开始漂移、重复、自相矛盾。50+ 步基本不可控。
- **每 3–5 步**：生产系统普遍设置人工检查点（human-in-the-loop），这是行业共识，不是保守。

### 失败的四个根因（不是模型笨，是脚手架问题）
1. **错误累积**：每步都可能错，长链把小错放大成大错。
2. **上下文退化**：计划写在上下文里，长任务中被挤掉后就"忘了目标"（plan eviction）。
3. **工具不可靠**：API 会变、网页会改、路径会不同——昨天能跑的今天可能挂。
4. **奖励作弊**：Agent 会优化你定义的指标本身，而不是你要的真实目标（Goodhart 定律）。

## 四、把边界映射回你的项目

你想要的"从 0 自动搭建 AI 漫剧并发布，只在关键点审批"，对照上面的边界：

- 这是一个 **几十步以上、跨多种工具、需要审美判断、要求高成功率** 的任务——恰好踩在每一条"做不到"上。
- 行业里已经跑通的方案（Dify + ComfyUI、OpenClaw、漫小芽等），聪明之处是**人写好了固定工作流**，AI 只在节点上执行；关键点仍由人审。
- "让 AI 自己搭工作流"属于 ADAS（自动设计智能体系统）研究方向，2026 年是前沿、有原型，但成本极高、评价器是瓶颈，不适合当产品交付。

**可行的路径**（已在前面几轮讨论中确认）：
1. 人肉跑通 1–3 集，记录每步输入输出和失败点 → 获得领域经验
2. AI 接管节点，人写的 checklist 变成硬验收标准 → 获得稳定产出
3. 让 AI 在已有流水线上做局部改动，用真实成片打分 → 才是自我改进

## 五、看任何 AI 项目时该问的五个问题

1. 它解决了谁的哪一个具体问题？（场景是否清晰）
2. 输入什么、输出什么、什么算成功？（成功标准是否可验证）
3. 这个流程多少步？有没有在 3–5 步处设人工检查点？
4. 哪几层是确定性的工程，哪层是概率性的 AI？边界划分对不对？
5. AI 出错时会怎样？有没有失败路径和回滚机制？

这五个问题，也是面试里讲"我怎么判断一个 AI 产品该不该做、该做到哪一步"的骨架。

## 六、术语速查

| 术语 | 白话解释 |
|---|---|
| RLS | 数据库自带的数据隔离，用户只能看自己的 |
| pgvector | 把内容变成数字向量存起来，支持"意思相近"的搜索 |
| Edge Function | 跑在离用户/数据库很近的无服务器代码 |
| 租约 lease | 任务认领后加的锁，超时自动释放，防止 worker 崩了任务卡死 |
| handoff | Agent 之间交接控制权 |
| human-in-the-loop | 流程中插入人工审批点 |
| context eviction | 上下文太长时挤掉早期内容，导致 AI"忘了目标" |
| reward hacking | AI 钻指标空子，优化数字而非真实目标 |
| ADAS | 让 AI 自动设计 AI 系统的研究方向 |
| generator–evaluator | 一个负责做、一个负责判的架构模式 |
