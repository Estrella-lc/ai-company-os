# Database audit and asynchronous task migration design

Audited on 2026-11-09 against project mcwkkmkgfienxrmfyvfl. The handover document's project ref contains an extra n; use the actual dashboard project. Evidence is in 2026-11-09-catalog.json. Only catalog queries and aggregate checks were executed; no schema, policy, grant or business data was changed.

## Findings

11 public tables, 87 columns, 15 policies, 33 constraints, 13 indexes; no public triggers returned. All 11 tables enable RLS but do not force it. Owners and service_role can bypass RLS by design; do not treat this as browser authorization.

The effective check confirms anon has TRUNCATE on tasks, authenticated lacks SELECT on tasks, and service_role lacks SELECT on agents. TRUNCATE is not governed by row policies. Revoke nonessential TRUNCATE/REFERENCES/TRIGGER separately; do not claim a remotely exploitable Data API truncate endpoint was demonstrated.

Tasks currently has zero rows. It has title, description, assigned_agent_id, status (pending), priority (medium), due_at, project_id, created_by and timestamps, but no durable execution fields. Status and priority are free text without CHECK constraints. Existing constraints are primary keys, two code uniqueness constraints and foreign keys; no queue or ownership trigger exists. Indexes cover only primary keys and the two code keys, not conversation history or queue lookup.

Most tables have a SELECT policy for one fixed CEO UUID but no matching authenticated SELECT grant. Conversations/messages also have permissive ownership policies: any authenticated user can create their own conversation and user messages. Their names do not enforce CEO membership. The fixed CEO read policy is ORed with ownership policies and can read other users' conversations. This is a single-CEO application today; do not silently reinterpret it as multi-tenant isolation. Before exposing async submission, explicitly verify the CEO user server-side as well as conversation owner. Never accept created_by from request JSON.

Messages validates sender shape in its INSERT policy only, not through a table CHECK; admin writes bypass that policy. Aggregate check found zero invalid sender_type records. No global sender constraint is proposed yet. The chat-specific new constraint only applies when reply_task_id is present.

## Incremental schema design

Draft SQL lives in supabase/drafts, deliberately outside automatically applied migrations. Apply 001 then 002 only after staging tests. 001 preserves tasks.status and historical data; execution_state is separate and NULL for legacy tasks. task_kind=chat_reply opts into new required fields. Preserve existing priority strings; scheduling will map urgent/high/medium/low explicitly with a stable creation/id tiebreaker.

Uniqueness on request_message_id ensures one job per user message, while owner/request_key supports submission retries. Compare immutable request/conversation/agent fields when returning an existing job; reject key reuse with a different payload. Message request/conversation composite FK prevents cross-conversation references. Worker RPCs must also enforce sender_type=user, agent binding and conversation owner. The FK alone does not implement authorization.

## Durable execution contract

Use tasks as the persisted queue, with an independently deployed worker process. Poll using service-role-only transactional RPCs. No Next.js fire-and-forget promises. Codespaces can run the worker for development but is not production scheduling or uptime.

Submit: authenticated CEO endpoint calls an atomic enqueue RPC after checking auth.getUser, CEO membership and conversation ownership. In the transaction recheck message ownership/agent and insert queued task plus audit event; conflict returns the exact existing task only if the payload matches. Return 202 with task ID immediately. Browser can SELECT tasks through RLS but cannot INSERT/UPDATE execution state directly.

Claim: service-role-only RPC uses SELECT FOR UPDATE SKIP LOCKED; select queued tasks whose available_at <= now() and attempt_count < max_attempts. Lock, increment attempt_count, issue fresh random lease_token, set running, started_at and lease expiry atomically. Initial lease 90 seconds, heartbeat every 20 seconds; all updates require matching task ID and token and an unexpired lease. Claim one task at a time initially.

Complete: in one database transaction lock the task, verify running and current unexpired lease, recheck linked conversation/message/agent, insert assistant message with reply_task_id, insert usage/audit records, and set succeeded/result/finished_at while clearing lease fields. Transaction rollback must undo all writes on failure. A unique reply_task_id prevents duplicate persisted replies. Retrying completion of a succeeded task returns the stored reply; a stale worker may not update a new lease. This provides at-most-one stored reply, not exactly-once provider billing.

Failure: explicit transient errors schedule queued with backoff and jitter (5, 20, 60 seconds), available_at and safe last_error_code, clearing lease. attempt_count is incremented only on claim. Terminal auth/config/invalid-input failures or exhausted attempts set failed and finished_at. Reaper locks expired running jobs and either requeues or fails them at the attempt limit. Do not overwrite cancellation or success. Cancellation locks a queued/running task and clears lease; provider cancellation is best effort and late completion must be rejected by the token/state check.

RPC functions will be implemented in the next migration: enqueue_chat_reply, claim_chat_reply, heartbeat_chat_reply, complete_chat_reply, fail_chat_reply, cancel_chat_reply, reap_expired_chat_replies. Prefer SECURITY INVOKER with explicit service_role grants; where SECURITY DEFINER is necessary use empty search_path, fully qualified names, strict role checks, and REVOKE EXECUTE FROM PUBLIC,anon,authenticated. Enqueue/cancel called via trusted backend only. No RPC is exposed by these draft files yet.

Polling: GET task checks CEO plus created_by and conversation ownership; return execution_state, safe failure code and reply message ID. Never expose lease_token or raw input/provider errors to browser. Refresh resumes active task by request_message_id. Rendering success requires that task's reply_task_id, not any historical assistant message. Keep synchronous reply endpoint behind a feature flag until async E2E passes.

Usage: record every actual model call, including fallback and failed calls, with task/attempt/model/duration and available tokens. Unknown usage is unknown, not fabricated zero; existing token NOT NULL defaults require a later accounting design before worker release. Do not infer zero cost from a timeout. Tool execution and payments/publishing remain outside this first chat worker.

## Deployment and rollback

1. Review audit snapshot and take a database backup. Restore a staging clone; run drafts there first. Confirm exact target project and the server's CEO allowlist. Fix project-ref notes without changing working environment secrets.
2. Apply additive 001 with bounded locks; run schema tests. Apply access 002 separately and rerun browser/worker access tests. Do not broaden other tables' browser grants merely because a policy exists.
3. Implement and test transactional RPCs plus worker before enabling async endpoints. Gate rollout to CTO only, concurrency 1, then enable polling UI. Existing synchronous route remains rollback path.
4. Rollback behavior: disable async feature flag, stop new submissions, drain or cancel existing jobs under row locks and stop workers. Revert app version. Keep additive columns/indexes and job/message records for recovery; do not drop them or delete history. Revisit grant changes separately using the recorded ACL snapshot, not GRANT ALL.

## Required verification before release

Run migration from the recorded baseline in disposable PostgreSQL/Supabase, then verify existing chat still works. Reject non-CEO and cross-owner submissions. Confirm browser cannot mutate jobs or TRUNCATE, and service_role has only needed table/function access. Race duplicate submissions and two workers; only one task/lease/reply may persist. Test lease expiry, stale completion, heartbeat, cancellation/completion race, retries exhausted, and transaction rollback between message insertion and task success. Restart worker/browser mid-call and verify eventual state and refresh recovery. Check both success and fallback usage/audit linkage. Isolated validation completed on PostgreSQL 17: reconstructed tables, columns, PK/UNIQUE/FK, RLS policies and grants from the audit; applied both drafts successfully; passed supabase/tests/async_foundation.sql for legacy compatibility, duplicate requests/replies, cross-conversation FK, lease shape, attempt limits and effective privileges. Test fixtures were rolled back. This is not a full Supabase staging clone: auth.uid was stubbed for DDL compilation, so real JWT/RLS behavioral tests and worker concurrency tests are still required. State-transition permissions and stale-worker rejection remain future RPC responsibilities, not implemented by these CHECK constraints.
